Scope
Shared Firestore collections, fields, enums and ownership
Requested decision
Approve one canonical data contract before any panel is changed. After approval, all three developers should use the same collection names, field names, value types and enum values.
This document is a proposal only. It does not deploy Firestore rules, migrate data, change Firebase access, or modify application code.
Purpose and current problem
Buyer, creator and admin screens currently read and write overlapping Firestore data with different names and shapes. Firestore accepts those variations, but the application then fails when one panel reads a document created by another panel.

Expected outcome
An order placed by a buyer is immediately readable by the assigned creator and the admin panel.
Admin order management and finance screens use the same order totals and status values as the creator and buyer panels.
Historical records remain readable during migration through temporary legacy aliases.
New writes stop introducing additional field-name variations.
Team conventions
Use lowerCamelCase fields and plural snake_case collection names.
Store enum values in lowercase snake_case. UI labels are presentation only.
Store MVP money as whole INR integers, not formatted strings.
Store dates as Firestore Timestamp values, never formatted strings.
Store addresses as maps, never as a single string.
Use null or omit an optional value instead of storing N/A.
New writes use only this schema. Legacy aliases are read only during migration.
All panels use one shared typed model and repository mapper. Screens do not cast raw Firestore maps independently.
Shared documents include schemaVersion with value 1.

Proposed MVP calculation
subtotal = sum(items.lineTotal)
buyerPayableAmount = subtotal + shippingAmount
commissionAmount = subtotal > 999 ? round(subtotal * commissionRate / 100) : 0
platformFee = min(subtotal, flatFee + commissionAmount)
creatorNetAmount = subtotal - platformFee
Approval required  Confirm whether the ₹50 flat fee is deducted from creator proceeds, as proposed above, or added to the buyer payable amount. Every panel must follow the same approved interpretation.

Migration guardrails
Do not delete or bulk-rewrite production data before a reviewed migration plan exists.
Do not remove legacy fallbacks until all production documents are verified.
Deploy Firestore rules and indexes only after explicit Firebase access approval.
Adoption plan
All three developers and the product owner approve this contract.
Freeze new Firestore field names until approval is complete.
Create one shared model, mapper and enum helper set under the shared order feature.
Add temporary legacy read fallbacks from the compatibility table.
Update buyer, creator and admin writers to write canonical fields only.
Update all screens to consume typed shared models instead of raw maps.
Backfill existing documents with a separately reviewed migration script.
Separately approve and deploy updated Firestore rules and indexes.
Verify production documents and then remove legacy fallbacks.
